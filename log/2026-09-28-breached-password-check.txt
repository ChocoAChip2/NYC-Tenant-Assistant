2026-09-28 -- Breached-password check (replacing a Supabase Pro feature)
=========================================================================

WHY

Supabase's security linter flags "Leaked Password Protection Disabled".
The built-in feature is gated behind a paid plan, so it was left open.

Have I Been Pwned's Pwned Passwords range API does the same job, free,
with no API key and no documented rate limit. password_safety.py wires it
into all three places a password can be set: signup, the password-reset
link, and the Settings password change.

This is arguably better than the Supabase setting would have been: it runs
on our own paths, so the wording, the threshold and -- most importantly --
the failure behaviour are ours, and all three are visible in this
repository instead of being a checkbox in a dashboard.

HOW THE PASSWORD STAYS PRIVATE

k-anonymity. We SHA-1 the password and send only the FIRST FIVE hex
characters of the hash. HIBP returns every hash suffix in the corpus
starting with those five characters -- typically several hundred -- each
with a count, and the comparison happens locally.

So the password never leaves the process, and HIBP cannot tell which of
the candidates sharing that prefix was being asked about. The request also
sets Add-Padding: true, which asks for decoy records so the RESPONSE SIZE
does not hint at how many real matches the prefix had.

TWO DELIBERATE SOFTENINGS -- DO NOT TIGHTEN THESE WITHOUT READING THIS

1. IT FAILS OPEN. Unreachable API, timeout, garbage response, non-numeric
   count: the password is allowed. A tenant who cannot make an account
   because a third party blinked is a worse outcome than a weak password
   on an account that already sits behind rate limiting and an
   exponentially-escalating login lockout. This is defence in depth, not a
   gate.

   times_breached() returns None for "unknown", which is deliberately NOT
   zero. is_breached() exists so that no call site can write
   `times_breached(...) > 0` and either crash on None or coerce it into a
   decision.

2. IT ONLY BLOCKS THE GENUINELY COMMON. BREACH_BLOCK_THRESHOLD is 100
   appearances. A password seen three times in a decade of breaches is a
   different risk from one on every credential-stuffing list, and blocking
   everything ever seen once teaches people to fight the form.

PASSWORD_BREACH_CHECK=off disables it entirely, for a deployment with no
outbound network access.

VERIFICATION

- 379 unit tests (up from 353); 26 new.
- No test touches the network: every one fakes the HTTP layer, so the
  suite does not depend on api.pwnedpasswords.com being up.
- Asserted directly that only five hex characters are ever sent, that the
  password itself never appears in the request, and that Add-Padding is
  set.
- Fail-open proven at the unit level AND end to end through the signup
  route: with the API timing out, the account is still created.
- All three routes asserted separately, because two of them already had a
  near-identical length check and a future copy-paste that dropped the
  breach line would otherwise be silent.
- Parser checked against a real-shaped CRLF range response: "password"
  resolves to its true breach count, an unrelated passphrase to 0.

NOTE ON THE SANDBOX

api.pwnedpasswords.com is blocked by the build sandbox's egress proxy, so
no live call was made from here. The request shape is asserted by test
instead. Worth one manual signup attempt with the password "password" on
Render after deploy to confirm the real endpoint is reachable from there.
