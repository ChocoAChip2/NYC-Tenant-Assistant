2026-10-11  Emailed sign-in codes and a stronger password rule

Request (owner, 2026-10-11; lifts the 2026-10-01 feature hold for this one
change):
1. Any new password must be at least 8 characters with a lowercase letter,
   an uppercase letter, a digit and a symbol.
2. An account with an older, weaker password can still sign in but must set
   a compliant one before any signed-in page. No skip. Logout still works.
3. Optional second step: a 6-digit code emailed at sign-in, turned on (and
   off) in Settings with a code.

Changed
- password_safety.py: one validator (unmet_rules / meets_rules) and the
  auth provider's exact symbol list. Used by sign-up, the reset link,
  Settings and the new /account/password page. Sign-up had no server-side
  length check before (only minlength="6" in the page); it has one now.
- Live checklist under every new-password field (_password_rules.html).
  All minlength="6" and "At least 6 characters" are gone.
- Forced change: login() checks the typed password and sets a session
  flag; a before_request gate holds every signed-in page (not just chat) on
  /account/password until a compliant password is saved. The gate lists
  what stays open, so new signed-in routes are covered by default.
- Sign-in codes (email_codes.py, /login/code, login_code.html): after a
  correct password on an account with the switch on, nothing is kept in
  the browser session but who it was for; the password step's session is
  ended; a code is emailed; the session returned by verifying the code
  becomes the tenant's session. Wrong codes count in login_lockout under
  the same key as wrong passwords. Resend waits 60 seconds.
- Settings: a "Sign-in codes" section. On and off both need an emailed
  code. The switch is user_metadata.email_code_signin, written through the
  tenant's own session and read from the sign-in response.
- login() session setup moved into a shared helper used by both sign-in
  paths. Order: password, code (if on), forced change, missing details.
- Password reset has no code step (the reset link already proves the same
  inbox).
- Checked in the installed client library: sign_in_with_otp, verify_otp
  and admin.sign_out(jwt, "local") exist with the shapes used here.

Not changed
- No database change, no new dependency, no new environment variable.
- The earlier idea of an RLS follow-up does not apply: the auth provider
  has no second-factor level to check for an emailed code.

What it protects against, and what it doesn't
- Stops someone who has only the password from signing in through the
  site.
- Adds nothing if the tenant's inbox is compromised.
- Enforced by the app, not below it. The switch lives in the account's own
  metadata, which the account's own session can edit.
