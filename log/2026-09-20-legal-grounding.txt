THE BUG THE PROPOSAL HAD, AND WHY THE GUARD LOOKS LIKE THIS

The original design (docs/grounded-sources.md) checked that every citation
marker pointed at a retrieved passage. docs/proposal-review.md found that
this is not enough, with a worked example:

  The assistant retrieves 27-2029 correctly and replies "Under 27-2029
  your landlord must keep it at 70F overnight."

Marker valid, section real, section retrieved -- and the overnight minimum
is 62F. The citation makes the wrong answer MORE convincing than an
uncited guess would have been. So the guard now also requires a verbatim
quote from the cited passage, and requires every number-with-a-unit in a
cited sentence to appear in that passage. The first test in
tests/test_citation_guard.py is that exact reply.

WHAT THE GUARD STILL DOES NOT DO

Fix retrieval. A wrong section, quoted perfectly, still misleads. Saying
otherwise would repeat the mistake this design was written to correct.

REPORT MODE IS THE DEFAULT

LEGAL_GUARD_MODE defaults to "report": log every violation, change
nothing. A guard that rejects good replies makes the assistant quietly say
less than it knows, and that failure looks like a dull model rather than a
bug. Measure the false-rejection rate from the logs first, then enforce.

THE WHOLE FEATURE IS OFF BY DEFAULT

LEGAL_CORPUS_ENABLED gates retrieval entirely. With it unset -- which is
the state on Render right now -- the chat path is byte-for-byte the
behaviour it had before this branch, and a test asserts that.

SECURITY FINDING FIXED ALONG THE WAY

The 20260920 migration created legal_documents with no RLS. Every public
table in Supabase is exposed through PostgREST, so that table was
writable by anyone holding the anon key, which ships in the browser. For
the store whose entire job is to be the thing the assistant trusts, that
is a prompt-injection vector rather than an anti-hallucination measure.
